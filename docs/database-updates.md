# Ordered database and Pages releases

## Normal release flow

After bootstrap, no manual database step is needed:

| Merge / push | GitHub environment | D1 database | Pages branch / deployment |
| --- | --- | --- | --- |
| `develop` | `database-preview` | `studentportal-preview` | `develop` / preview |
| `master` | `database-production` | `studentportal-db` | `master` / production |

`.github/workflows/release.yml` (**Release Studentportal**) checks out `github.sha` for the whole release. It installs locked root/frontend dependencies, runs root TypeScript/backend tests and frontend tests, builds frontend and Pages Functions, lists/applies/verifies target migrations, then deploys that prebuilt output to the existing `availogger` Pages project. No revision is resolved again from a moving branch. Pages receives `--commit-hash <SHA>`; Actions summary/deployment metadata identifies the same revision.

The Functions generated by `npm run functions:build` are copied into `frontend/dist/_worker.js/`, including relative modules. Existing `_routes.json` retains `/api/*`; the generated bundle retains Access middleware, API file routing and the ASSETS fallback. `wrangler pages deploy ... --no-bundle` uploads the compiled worker instead of compiling new Functions after migration. The Wrangler action uses the version installed from the tested lockfile. This is a Pages deployment, not a standalone Worker. [Cloudflare advanced-mode output](https://developers.cloudflare.com/pages/functions/advanced-mode/), [Wrangler CI upload](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/).

For D1, preview selects `--env preview` in root `wrangler.jsonc`. Pages deployment uses **`--branch develop` or `--branch master`**, not `--env` or a custom `--config` flag (Pages does not support those deployment flags). Wrangler selects the Pages configuration by comparing the branch with the project's production branch. Preflight checks that the existing project is `availogger`, production branch is `master`, and D1/KV resources remain distinct. [Pages configuration](https://developers.cloudflare.com/pages/functions/wrangler-configuration/).

Only `push` and explicit `workflow_dispatch` on exact `refs/heads/develop` / `refs/heads/master` can release. Feature branches, PR merge refs, tags and other events are rejected. There is no database-target/source dropdown. PR CI in `ci.yml` continues TypeScript, backend/frontend tests, frontend build and Functions build, using only disposable local databases. Direct trusted-branch pushes receive the same release validation; a previous PR check is not sufficient.

## Enable controls

Create **repository Actions variables**, not environment variables, because the planning job must decide before requesting an environment:

- `AUTO_RELEASE_PREVIEW=true` enables automatic develop releases.
- `AUTO_RELEASE_PRODUCTION=true` enables automatic master releases.

Missing values, `false`, `TRUE`, or anything other than lowercase `true` disable automatic releases without a bootstrap error. The planning summary names the missing control; the remote job is skipped. The controls are independent. Manual **Run workflow** is an explicit recovery/bootstrap action and bypasses the automatic enable controls, while retaining all branch, SHA, environment, validation and migration gates.

Automatic push releases also refuse to start migrations while that target's independent Pages Git deployments are enabled. This avoids two competing deployers after cutover. Manual releases allow the initial verification while Git deployment remains available. Do not enable automation or merge schema-dependent features until the cutover below is complete.

## One-time setup: exact UI actions

### 1. Cloudflare API token

1. Cloudflare dashboard → profile icon → **My Profile → API Tokens → Create Token** (or **Account API Tokens**).
2. **Custom token → Get started**; name it `Studentportal releases`.
3. Add **Account → D1 → Edit** and **Account → Cloudflare Pages → Edit**.
4. **Account Resources → Include → Specific account**: choose the account containing `availogger` and both D1 databases.
5. **Continue to summary → Create Token**; save its value securely.

Update existing D1-only tokens or replace them with this token. Do not add DNS, Access administration, KV Edit, Workers deployment or account-wide unrelated permissions. D1/Pages account permissions cover resources in the selected account; separate preview/production tokens do not provide per-database isolation by themselves. [Cloudflare token setup](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/#generate-an-api-token).

### 2. GitHub environment secrets and branch rules

1. GitHub → **1ntray/availogger → Settings → Environments**.
2. Open/create **database-preview**. Under **Deployment branches and tags**, choose **Selected branches and tags** and allow the branch **develop** only; no tags or feature branches.
3. Under **Environment secrets**, add/update `CLOUDFLARE_API_TOKEN` with the token above and `CLOUDFLARE_ACCOUNT_ID` with the Cloudflare **account ID**, not a D1 ID.
4. Repeat for **database-production**, allowing only branch **master**, with the same secret names and a token authorized for the correct account.
5. If the old preview environment allowed master too, remove that extra rule. Optional production required reviewers depend on GitHub plan/visibility; enabling them adds an approval before the job, though migrations remain automatic once approved. For releases with no per-run intervention, omit required reviewers.

Keep Pages **runtime** secrets in Cloudflare → **Workers & Pages → availogger → Settings → Variables and secrets**, configured separately for Production/Preview: `CF_ACCESS_TEAM_DOMAIN`, `CF_ACCESS_AUD`, `FLIGHTLOGGER_CREDENTIAL_ENCRYPTION_KEY`, and `PORTAL_BOOTSTRAP_ADMIN_SUBJECT` where already used. Do not copy them to GitHub or any `VITE_*` variable. Existing D1/KV bindings, encryption keys, Access policies, domain and Wix DNS are unchanged.

### 3. GitHub repository variables

GitHub → **Settings → Secrets and variables → Actions → Variables → New repository variable**. Create `AUTO_RELEASE_PREVIEW` and `AUTO_RELEASE_PRODUCTION`, initially **`false`**. Keep them at repository scope; environment-scoped overrides are not supported by the planning gate. Enable each only at the corresponding cutover step.

### 4. Branch protection

GitHub → **Settings → Branches → Add branch protection rule** (or equivalent **Rulesets**). Protect `develop`, then `master`:

1. Enable **Require a pull request before merging**, with review requirements appropriate to the project.
2. Enable **Require status checks to pass**; select the existing CI **backend** and **frontend** checks after they have run on the PRs. Enable **Require branches to be up to date** if available.
3. Disable force pushes and branch deletion; avoid bypass rights for routine direct pushes.
4. Do not require the post-merge release job as a PR check: it deliberately does not run on pull requests.

### 5. Cloudflare branch controls — only after verification

After the workflows exist on both branches, credentials are configured, and a manual preview release succeeds:

1. Cloudflare → **Workers & Pages → availogger → Settings → Builds & deployments / Build → Branch control → Edit**.
2. Keep **Production branch: master**. Uncheck **Enable automatic production branch deployments** when switching production.
3. Under **Preview deployments**, select **None** when switching preview.
4. **Save**. Check the saved settings. Do not disconnect Git, delete the project, change the production branch or create a new project.

Cloudflare labels may be grouped under **Configure Production deployments** / **Configure Preview deployments**. These switches stop future Git builds; they do not take the currently deployed site offline. Wrangler can still upload to the same Git-integrated project. [Branch controls](https://developers.cloudflare.com/pages/configuration/branch-build-controls/), [Git-integrated uploads](https://developers.cloudflare.com/pages/get-started/direct-upload/).

## Safe bootstrap and enable order

1. Set both repository variables to **false** (or leave absent). Leave existing Pages Git deployments running.
2. Review/merge the **master bootstrap PR based on master**. It contains tooling/docs/tests only and existing migrations `0001–0003`; do not merge all develop to master to obtain workflows. Its disabled push release cannot migrate/deploy through Actions. Existing Git integration may rebuild the unchanged application.
3. Review/merge the **develop automation PR**. It keeps current features and the reviewed `0005` fix. Both branches now have the workflow; the master/default-branch copy makes **Run workflow** visible. [GitHub manual-workflow requirement](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).
4. Configure token permissions, environment secrets/branch rules and branch protection above. Keep variables false. Briefly pause merges during the switchover and let any existing Pages Git builds finish; do not leave older Git builds queued to overwrite an Actions deployment.
5. GitHub → **Actions → Release Studentportal → Run workflow → Branch: develop → Run workflow**. This explicitly tests preview despite automation being off. Confirm validation, migration verification, deployment and Access-protected `/api/me` / availability succeed. It must report a **preview** deployment for **develop** and the tested SHA. Keep Git deployment active until this test succeeds.
6. Set Pages **Preview deployments: None**, save, then set repository **AUTO_RELEASE_PREVIEW=true**. Dispatch develop again to verify upload still works with Git builds off. Preview now has a tested recovery path and automatic releases.
7. When ready to switch production, manually **Run workflow → Branch: master**. Review pending existing production migrations first. This releases only master, not develop features. Verify `student.luftfartsfag.no`, authenticated `/api/me` and an uncached availability date range. If it fails, keep production Git deployment enabled and fix the workflow/credentials.
8. After that success, uncheck automatic **production** branch deployments, save, then set **AUTO_RELEASE_PRODUCTION=true**. Dispatch master again to prove the new production path works with Git builds disabled. Resume merges.
9. Future PR merges need no manual migration. Promote develop features through the normal reviewed PR to master only when ready; the master pipeline applies that commit's migrations before publishing its code.

The bootstrap master PR must not contain Duty Ops swaps, transport, migrations `0004/0005`, or other unrelated application features. The same release tooling is shared between both PRs. Neither PR is merged automatically by implementation.

## Recovery and manual fallback

**Preferred:** GitHub → **Actions → Release Studentportal → Run workflow** → choose **develop** for preview or **master** for production. No other input is accepted. This pins the selected branch's SHA at dispatch and repeats validation/build/migration/deployment. To retry the same failed revision, open its run → **Re-run failed jobs** / **Re-run all jobs**. Before rerunning an older revision after a newer release, verify schema/code compatibility; use a fresh dispatch for current branch code if unsure.

**Database only:** **Actions → Update database → Run workflow**, choose develop/master. It checks the selected exact SHA, TypeScript/backend tests, then lists/applies/verifies only that branch's fixed database. It never deploys Pages or applies develop SQL to production. Use only for deliberate recovery/schema preparation; normally use the complete release. Both workflows share `studentportal-release-<ref>` concurrency with `cancel-in-progress: false`, so a fallback cannot race a release on the same target. GitHub keeps an active run and at most one pending run; newer queued runs may replace pending ones, and ordering is not FIFO. Never cancel an active migration as routine release management. [Concurrency semantics](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).

CLI fallback from the repository root after `npm ci`, in the reviewed target checkout:

| Target | Apply | Status |
| --- | --- | --- |
| Local | `npm run db:migrate:local` | `npm run db:status:local` |
| Preview | `npm run db:migrate:preview` | `npm run db:status:preview` |
| Production | `npm run db:migrate:production` | `npm run db:status:production` |

Authenticate local Wrangler using `npx wrangler login`. CLI operations bypass the Actions lock; use them only when no release/fallback job is active. No pending migrations is a normal no-op.

## Failure behavior and migration policy

- **Install, tests or build fail:** no remote migration/deployment step runs. PRs never mutate remote resources.
- **D1 list/apply/history verification fails:** deployment is skipped. Wrangler logs identify the failing migration; the Actions summary reports the failed stage. The failed migration rolls back, but earlier successful files remain applied. Never mark a failed file as applied or reset `d1_migrations`.
- **Migration succeeds, deployment fails:** schema stays applied and the existing Pages deployment normally remains active. No automatic rollback. Fix deployment/credentials and rerun; applied files are skipped. If upload succeeded but metadata/status reporting failed, inspect the Pages deployment before assuming the old version is still live.
- **Automation disabled:** planning succeeds with a clear disabled summary; the remote job is skipped. Explicit manual recovery is still available.

Migrations are versioned and immutable after successful release. Normal automated changes must be additive/backward-compatible with the currently deployed application, because deployment may fail after migration. Use **expand → migrate data/usage → contract** for destructive changes, spanning deliberate releases. An application rollback is not a database rollback; restoring code requires compatibility with applied schema. There is no automatic SQL repair, rollback, infrastructure deletion or runtime-secret change.

`migrations/*.sql text eol=lf` in root `.gitattributes` enforces LF checkouts on Windows; Git stores migration files with LF. The release rejects CR characters before applying SQL. The reviewed `0005_transport.sql` correction avoids nested CASE/END inside its passenger trigger while preserving integrity checks; it remains intact. This was an equivalent syntax correction for a failing pending migration, not permission to rewrite successfully applied schema migrations. A later correction to an applied migration must use a new version. [D1 migrations](https://developers.cloudflare.com/d1/wrangler-commands/#d1-migrations-apply).

## Verification checklist

1. **Develop merge:** merge a small reviewed non-schema PR after preview cutover. Open its push **Release Studentportal** run. Verify SHA = merge SHA, tests/build precede **List, migrate and verify target D1**, logs name `studentportal-preview` and say no pending files, then Pages deployment succeeds. In Cloudflare **availogger → Deployments**, verify **Preview / develop / same SHA**. Sign in and open `/api/me` (JSON), `/api/availability?...` and the portal; production deployment ID must not change.
2. **Master merge:** repeat through a reviewed master PR after production cutover. Logs must name `studentportal-db`; Cloudflare must show **Production / master / same SHA**. Verify the custom domain and API; preview deployment must not change.
3. **Failure gate without corrupt SQL:** local tests simulate a failed apply and missing migration history. For an optional live preview-only drill, temporarily replace only `database-preview`'s token with a **Pages Edit only** token, dispatch develop, and confirm the D1 stage fails and **Deploy** is skipped; compare Pages deployment IDs. Restore the D1 + Pages token and rerun. Do not change production credentials or introduce intentionally invalid SQL into master/develop.
4. **Manual rerun:** dispatch develop again or rerun the same failed run after fixing credentials. Already-applied SQL is a no-op; deployment records the pinned SHA. Check summaries and Functions JSON responses again.
5. **Disabled gate:** set only `AUTO_RELEASE_PREVIEW=false`, push a harmless reviewed develop change, and check the plan summary names the variable and the remote job is skipped. Restore true. Production is independent.

Implementation tests never call live Cloudflare/FlightLogger, apply remote migrations or publish Pages. Live cutover verification is performed by the administrator after merging and configuring these workflows.

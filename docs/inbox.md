# Personal Inbox

`user_inbox_items` stores a personal pointer to a source record and a nullable `read_at`. The Inbox is available at `/inbox`, with a quiet unread badge in the header and a link in the account menu. It is not a new mobile bottom-bar destination. There is no endpoint for a client to send an item to an arbitrary user.

Inbox, Needs Attention, Contact status, and Activity are distinct. Reading an item changes only `read_at`; it never resolves a contact thread, fuel request, swap, or other operational record. Source records own their state and history. No push, email, subscription, or notification permission is implemented here. Future push can react to a server-created relevant item after subscription and delivery rules are designed separately.

`GET /api/inbox` returns the current authenticated user's latest 30 items by default (maximum 50 via `?limit=`), an unread count, and a cursor for the next page. Order is `created_at DESC, id DESC`; the cursor carries those two fields. The resolver in `backend/inbox.ts` maps each `source_type` to a title, summary and target. `FLIGHT_CHANGE` retains detailed non-addition flight changes. `SCHEDULE_CHANGE` renders raw Duty Ops/Flyvask removal and time changes. `SCHEDULE_NOTIFICATION_GROUP` renders unread assignment additions coalesced per user/domain until read. `EXCHANGE` resolves relevant Exchange v2 targets and candidates with a safe module route and exchange ID. `CONTACT_NOTIFICATION` resolves thread-level feedback and reply notices with permission-aware targets. Historical `CONTACT_MESSAGE` rows remain readable. Missing, unknown or inaccessible sources render as unavailable without exposing content or an unsafe target. Future domains should derive recipients under their own authorization rules and add a resolver. `POST /api/inbox/:itemId/read` has an empty body, requires same-origin request checks, sets server time once, and is idempotent. Reading a group closes it atomically, so later events start a new group. Another user's ID returns the same 404 as a missing ID. Both endpoints use the existing Cloudflare Access application-user identity and `Cache-Control: no-store`; no new role permission is needed for one's own Inbox.

See [schedule notifications](schedule-notifications.md) for raw FlightLogger baselines, grouping, Contact lifecycle, and Exchange relevance rules.

Source events and Inbox items have no retention job yet; pagination bounds response size, and a later retention policy can be designed separately.

Opening an item marks that one Inbox pointer read before navigating to its source route. A slow read request may finish after client-side navigation, with the header unread badge refreshed on completion. Visiting `/inbox` alone never changes read state. "Mark read" and "Open" do not accept, resolve, or otherwise mutate the source flight change, contact thread, or exchange. The read route accepts a genuinely empty POST even if Pages represents it as a zero-byte request stream; nonempty bodies, invalid IDs, cross-origin calls, and other users' items remain rejected.

# Flight schedule changes

Studentportal keeps FlightLogger read-only. A complete, successful personal flight sync compares bounded operational fields with the previous shared `flights` row inside the same D1 batch that updates that row. One canonical transition creates one `flight_change_events` record and up to nine `flight_change_items` field snapshots. `flight_students` determines currently proven recipients; each gets a separate personal Inbox item. Other FlightLogger credentials are never used to validate or deliver a change.

The tracked fields are planned flight and booking start/end, aircraft ID/callsign/model, instructor ID/name, departure and arrival airport ID/name, and cancellation/restoration. Routine completion, unchanged data, and presentation-only name changes do not alert. Time comparisons use UTC ISO values, and the API presents the operational flight time first. When booking and flight times move together, the audit retains both fields while the summary says “Time changed” once. Aircraft changes still move existing fuel requests to `NEEDS_REVIEW`; that fuel state and the Inbox are independent consequences.

The first successful sync is a baseline. Replacing a FlightLogger key clears that user's observed memberships and sync state, establishing another baseline. A later new or missing booking is announced only inside the overlap of the previous and current successful windows. No event is inferred from a failed, rate-limited, truncated, or partially paginated fetch. A user-specific removal is recorded before their membership is removed. A new booking is recorded after the canonical upsert and before the new membership is inserted.

The comparison, event/items, Inbox writes, canonical upsert, fuel review, membership changes, and sync-state update run in one D1 batch. [Cloudflare documents D1 batches as sequential transactions that roll back on failure](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch). The old row is compared before it is overwritten; a second sync of the same upstream state sees no transition. There is no permanent old/new-value dedupe, so a later A → B → A → B sequence remains visible. Event history stores booking/time/aircraft snapshots and survives routine canonical flight cleanup (`flight_id` becomes null).

`0011_flight_changes.sql` is additive after `0010_brakkevakt.sql`. Do not edit either migration after release. The normal release workflow applies it to preview before preview deployment and to production before production deployment. To verify locally: `npm run db:migrate:local`, then `npm run db:status:local`. Do not apply this migration to a remote database directly from a feature branch.

Limits: a personal FlightLogger sync proves only that account's own visibility, and `flight_students` is a snapshot rather than real-time cross-account discovery. If two students observe different upstream states at different times, the canonical transition is recorded when the first complete sync writes it. This is an in-app history, not an upstream acknowledgement or a push notification.

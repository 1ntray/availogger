# Personal Inbox

`user_inbox_items` stores a personal pointer to a source record and a nullable `read_at`. The Inbox is available at `/inbox`, with a quiet unread badge in the header and a link in the account menu. It is not a new mobile bottom-bar destination. There is no endpoint for a client to send an item to an arbitrary user.

Inbox, Needs Attention, Contact status, and Activity are distinct. Reading an item changes only `read_at`; it never resolves a contact thread, fuel request, swap, or other operational record. Source records own their state and history. No push, email, subscription, or notification permission is implemented here. Future push can react to a server-created relevant item after subscription and delivery rules are designed separately.

`GET /api/inbox` returns the current authenticated user's latest 30 items by default (maximum 50 via `?limit=`), an unread count, and a cursor for the next page. Order is `created_at DESC, id DESC`; the cursor carries those two fields. The resolver in `backend/inbox.ts` maps each `source_type` to a title, summary and target. `FLIGHT_CHANGE` retains the flight snapshot and changed fields. `EXCHANGE` resolves relevant Exchange v2 targets and candidates with a safe module route and exchange ID. `CONTACT_MESSAGE` resolves to the owning student's contact thread and latest webmaster reply, targeting `/messages/:threadId`. One item per contact thread is renewed and made unread after another webmaster reply; student replies create no Inbox item. Missing, unknown or inaccessible sources render as unavailable without exposing content or an unsafe target. Future domains should derive recipients under their own authorization rules and add a resolver. `POST /api/inbox/:itemId/read` has an empty body, requires same-origin request checks, sets server time once, and is idempotent. Another user's ID returns the same 404 as a missing ID. Both endpoints use the existing Cloudflare Access application-user identity and `Cache-Control: no-store`; no new role permission is needed for one's own Inbox.

Source events and Inbox items have no retention job yet; pagination bounds response size, and a later retention policy can be designed separately.

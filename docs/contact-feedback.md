# Contact & Feedback

Students send feedback at `/feedback` using only category and message. The current same-app page path is optional and selected by default. The server accepts `BUG`, `IMPROVEMENT`, `IDEA`, or `OTHER` and a 1–4000-character message, derives a concise title, and never accepts a recipient, author, subject, email, attachment or arbitrary metadata from the client. It stores only a bounded path without query or fragment; screenshots, logs, browser data, tokens and local storage are not collected. The authenticated account supplies identity. Students see and reply to their own conversations at `/messages`; the UI renders all message text as React text.

Migration `0013_contact_messages.sql` introduces `contact_channels`, `contact_threads`, and append-only `contact_messages`, plus the privileged `contact.webmaster.manage` catalogue key and ADMIN grant. The initial active user-facing channel is `webmaster`. Future channels can use the same schema with an explicit recipient permission and separate server-side routing. Student creation is fixed to webmaster; they cannot choose a recipient or see other students' threads. Effective permissions, including DENY overrides, govern webmaster list, detail, reply and status APIs. The webmaster sees `/admin/contact`, filters open/resolved threads, replies, and resolves/reopens. Any reply reopens a resolved thread; messages remain immutable. Threads and Inbox rows are separate records. A webmaster reply to another user renews one personal Inbox item for that thread. A student reply, including one on a resolved thread, does not notify the student.

`GET/POST /api/contact`, `GET /api/contact/:threadId`, and `POST /api/contact/:threadId/reply` are student endpoints. The analogous `/api/admin/contact` endpoints and `POST /api/admin/contact/:threadId/status` require `contact.webmaster.manage`. Mutations check same origin, bound JSON input and allowed fields. Lists are limited to 50 per page; a conversation is capped at 200 messages. The database batch guard rechecks channel, ownership or effective permission during writes. The APIs return no-store responses and do not mutate FlightLogger, schedules or swaps.

Exchange v2's `0012_exchange_v2.sql` now precedes `0013_contact_messages.sql` on `develop`. This feature adds only 0013 and does not modify 0012. The shared Inbox resolver handles Exchange, Contact and flight-change sources. Release automation applies pending migrations before code deployment. Deploying new code before 0013 would make contact and Inbox queries fail, so review the migration order and CI before release. No remote migration or deployment is part of this PR.
